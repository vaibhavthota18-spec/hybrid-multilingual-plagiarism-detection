## 1. Canonical Terminology & Ontology

To prevent semantic confusion, inconsistent variable naming, and API contract drift across engineering teams, the following terms are formally defined as the canonical domain vocabulary:

### Document
A digital file uploaded to the platform in PDF, DOCX, or TXT format. Once processed, a document comprises extracted text, structural metadata (page count, paragraphs, title), and ownership/tenant bindings.

### Submission Document
The primary target document submitted by a user for originality analysis and similarity inspection.

### Reference Document
A secondary document against which the submission is compared. A reference document may be provided ad-hoc by the user (Modes A & B) or retrieved from an indexed repository (Mode C).

### Reference Collection (Corpus)
A logical container of reference documents grouped under specific access controls (permissions) and ownership scopes, with pre-indexed fingerprints and vector embeddings.

### Passage
A discrete, coherent textual chunk extracted from a document. In this system, passages are bounded windows of approximately 100–300 words (or 500–1,500 characters) segmented along natural paragraph or sentence boundaries, serving as the fundamental unit of indexing and retrieval.

### Fingerprint
A deterministic, compact rolling-hash integer produced by the Winnowing algorithm representing a specific $k$-gram substring within a sliding window. Fingerprints identify exact verbatim substrings.

### Embedding
A 768-dimensional dense numerical vector generated by the multilingual transformer model (`intfloat/multilingual-e5-base`) capturing the semantic, contextual, and cross-lingual meaning of a passage.

### Candidate
A reference passage identified during Stage 1 retrieval (via Winnowing hash match, BM25 keyword score, or pgvector dense cosine similarity) deemed sufficiently similar to warrant detailed verification.

### Finding (Similarity Finding)
A verified instance of text reuse between a submission passage and a reference passage, characterized by precise character boundaries, similarity category (Exact, Near-Exact, Paraphrase, Translation), and source attribution.

### Alignment (Local Alignment)
The token-level sequence comparison process (using a modified Smith-Waterman local alignment algorithm) that maps the exact character span in the submission to the corresponding character span in the source.

### Matching Coverage
The mathematically deduplicated percentage of the submitted document that corresponds to verified matching passages:
$$\text{Coverage} = 100 \times \frac{\text{Unique Verified Matching Code Points}}{\text{Eligible Submitted Code Points}}$$
Reported separately as **Lexical Coverage** and **Potential Semantic Coverage**.

### Semantic Similarity
The cosine similarity between unit-normalized dense embeddings:
$$\text{sim}(u, v) = u \cdot v = \sum_{i=1}^d u_i v_i$$
Cosine similarity measures semantic closeness in vector space. **It is an evidentiary metric, NOT a probability of plagiarism.**

### Source Attribution
The unambiguous metadata linkage connecting a detected finding to its origin document, author, page number, and paragraph index.

### Evidence Strength
A composite qualitative/quantitative measure (High, Moderate, Low) reflecting alignment length, token overlap ratio, and vector cosine similarity.

### Human Review
An interactive workflow enabling educators, reviewers, or investigators to tag a finding as `VALID_CITATION`, `SUSPECTED_PLAGIARISM`, `FALSE_POSITIVE`, or `IGNORED`, updating net scores accordingly.

### False Positive
A flagged similarity finding that does not represent academic dishonesty or improper copying (e.g., standard boilerplate, mathematical definitions, common idioms, or properly cited quotations).

### Retrieval Recall (Recall@K)
The proportion of true relevant source documents or passages present in the top-$K$ candidates returned by Stage 1 retrieval.

## 2. Verified Architectural Decisions

The following elements represent locked, verified engineering decisions:
1. **Zero-Based Code-Point Offsets:** All backend offsets use Unicode code points (`[start, end)`), preventing character truncation or alignment drift across multi-byte Indic scripts.
2. **Dual Coverage Scores:** Verbatim matches and semantic paraphrases are reported as separate metrics to avoid conflating exact copying with conceptual similarity.
3. **Two-Stage Pipeline:** Stage 1 performs coarse candidate retrieval; Stage 2 performs granular token-level local alignment.
4. **PostgreSQL + pgvector:** Vector search is unified with relational state in PostgreSQL, avoiding multi-database synchronization overhead.
5. **Private by Default:** User uploads are never published to public corpora without explicit authorization.

## 3. Assumptions Log & Uncertainty Boundaries

The following assumptions underpin current design estimates and require empirical validation during implementation phases:

| ID | Assumption | Validation Phase | Risk / Impact if False |
|---|---|---|---|
| **ASM-001** | `intfloat/multilingual-e5-base` will provide sufficient cross-lingual transfer for Telugu without fine-tuning. | Phase 5 (Evaluation) | High. If Telugu cross-lingual recall falls below 70%, model fine-tuning or LaBSE fallback will be required. |
| **ASM-002** | Exact vector search in pgvector (`<#>`) will maintain $<500$ ms latency for corpora up to 10,000 documents on 8 CPU cores. | Phase 4 & Phase 7 | Moderate. If latency degrades, HNSW indexing will be enabled per ADR-0004. |
| **ASM-003** | PyMuPDF text extraction will reliably parse Indic text streams without Devanagari/Telugu glyph reordering errors. | Phase 2 (Ingestion) | Moderate. May require specialized Indic text re-ordering or font cmap fallback normalization. |
| **ASM-004** | A 10-page document (approx. 3,500 words) can complete full hybrid analysis within 180 seconds on CPU-only infrastructure. | Phase 5 & Phase 7 | Moderate. If CPU inference is too slow, batch size tuning or ONNX quantization will be triggered. |
| **ASM-005** | Quotation extraction using regular expressions and punctuation rules can accurately capture $\ge 85\%$ of legitimate academic citations. | Phase 6 (UX & Review) | Low. Reviewers can manually toggle spans via the human-in-the-loop review interface. |
